## 1. 竞品分析

### 1.1 市场背景

PC 端语音输入是一个已被验证的真实需求。Windows 和 macOS 有系统级语音输入（Win+H / Dictation），但 Linux 桌面几乎没有可用的系统级语音输入方案。用户在 Deepseek 网页端、腾讯 CodeBar、各类浏览器等不具备内置语音输入的场景下，只能手动打字。

"手机做语音识别 → 文字同步到 PC 剪贴板 → 用户手动 Ctrl+V"是当前空白市场的最轻量解法：复用用户手机上已安装的输入法语音能力，不引入额外语音引擎，不走云端，局域网直连。

### 1.2 竞品矩阵

| 产品 | 桌面端 | 手机端 | 语音引擎 | 连接方式 | 定价 | 开源 |
|---|---|---|---|---|---|---|
| **VoiceBridge / airmic** | Linux X11 | 浏览器 | Web Speech API | WebSocket + QR | 免费 | ✅ |
| **InsertKit** | Win/Mac/Linux (Tauri) | Android (Kotlin) | AI 云端 ASR | 账号云同步 | 订阅制 | ❌ |
| **VoicePad AI** | Win/Mac | Android/iOS | 本地 Whisper | WiFi + USB | 买断 | ❌ |
| **Voicy** | 全平台 | Android/iOS | 云端 ASR | 账号 | $6.79/月起 | ❌ |
| **Invoke** | Win/Mac/Linux (Python) | 无 | 本地 Whisper GPU | 无（本机） | 免费 | ✅ |
| **BeeType（本品）** | Win/Mac/Linux (Tauri) | Android/iOS (Flutter) | 复用手机输入法 | 局域网 TCP + QR | 免费 | 计划开源 |

### 1.3 逐产品分析

#### 1.3.1 VoiceBridge / airmic

- **技术路线**：手机浏览器打开 PC 提供的 Web 页面 → 通过 Web Speech API 做语音识别 → WebSocket 传回 PC → xdotool 注入到当前焦点窗口
- **亮点**：零安装（浏览器即用）、QR 配对、开源、支持中继服务器跨网络使用
- **短板**：
  - 浏览器 Web Speech API 在非 Chrome 浏览器或非 HTTPS 环境下不可用
  - Linux 端依赖 xdotool 键注入，在部分桌面环境（如 Deepin 25 + fcitx5）被拦截
  - 不支持 Wayland
  - 浏览器方案无法做到"松手即发"——需要点击网页上的按钮控制录音
- **与本品的关系**：最接近的竞品。本品用原生 APP 替代浏览器，解决"松手即发"和 IME 复用问题；用剪贴板替代 xdotool，解决键注入兼容性问题。

#### 1.3.2 InsertKit

- **技术路线**：Tauri + Rust + React 桌面端，Kotlin Android 端，账号制云同步
- **亮点**：桌面端用 Tauri（验证了 Tauri 在此类工具中的可行性）、功能丰富（文本扩展、剪贴板历史、AI 语音）
- **短板**：
  - 订阅制，文字过云端，隐私敏感
  - 走云同步而非局域网直连，延迟受网络影响
  - 功能过重，核心语音上屏被淹没在文本管理功能中
- **与本品的关系**：技术栈选型参考（Tauri）。本品聚焦单一功能（语音→剪贴板），不做文本管理。

#### 1.3.3 VoicePad AI

- **技术路线**：各平台原生应用，内置 Whisper 模型做 100% 离线语音识别
- **亮点**：完全离线、隐私好、自带 Whisper 模型
- **短板**：
  - 不支持 Linux 桌面
  - APP 包体大（Whisper 模型内置）
  - 不复用用户已有的输入法语音能力，而是自建引擎
  - 付费产品
- **与本品的关系**：本品不自带语音引擎，复用用户手机上已有的输入法（豆包/讯飞/微信），包体更小、识别质量由用户选用的输入法决定。

#### 1.3.4 Voicy

- **技术路线**：跨平台原生 + 浏览器，云端 ASR
- **亮点**：50+ 语言、AI 重写、自动标点
- **短板**：
  - 订阅制（$6.79/月起）
  - 语音数据过云端
  - 非局域网，延迟受网络质量影响
- **与本品的关系**：本品局域网直连，零延迟、零云端成本、隐私不外泄。

#### 1.3.5 Invoke

- **技术路线**：Python CLI，本地 Whisper GPU 转录，按住鼠标侧键说话
- **亮点**：开发者向、本地 GPU、无网络依赖
- **短板**：
  - 无手机端，纯 PC 本机方案
  - 需要 GPU 才能流畅运行
  - 不复用输入法
- **与本品的关系**：本品用手机做语音识别（用户已有的输入法），不需要 PC 有 GPU，也不需要安装 Whisper 模型。

### 1.4 差异化定位

| 维度 | 竞品主流方案 | BeeType（本品） |
|---|---|---|
| 语音引擎 | 自建（Whisper/云端 ASR） | **复用用户手机输入法** |
| 连接方式 | 云同步 / 浏览器 WebSocket | **局域网 TCP 直连** |
| 延迟 | 200ms~2s（受网络/云端影响） | **<50ms（局域网直连）** |
| 安装成本 | 装 APP + 注册账号 | 装 APP + QR 扫码，无账号 |
| 隐私 | 文字过云端 / 本地 Whisper | **文字仅在手机→PC 两跳，不过云端** |
| Linux 支持 | 仅 VoiceBridge（xdotool 有坑） | **Tauri clipboard 全平台原生支持** |
| 自动粘贴 | xdotool 键注入（兼容性差） | **不自动粘贴，用户手动 Ctrl+V（零兼容问题）** |
| 价格 | 订阅制 / 买断 | **免费开源** |

### 1.5 竞争壁垒

1. **复用输入法而非自建引擎**：用户已在输入法中训练了识别习惯（词库、联系人、习惯用语），切换到 Whisper 等新引擎反而会降低识别准确率。本品直接用用户已有的输入法，零迁移成本。
2. **局域网直连**：零延迟、零服务器成本、零隐私风险。竞品走云同步的产品在延迟和隐私上天然劣势。
3. **剪贴板而非键注入**：绕过了 Linux 桌面环境对模拟按键的拦截问题（XTEST/Wayland 限制），兼容性 100%。
4. **Tauri + Flutter 技术栈**：Rust 后端保证性能和安全，Tauri 保证跨平台原生安装包，Flutter 保证移动端一致体验。InsertKit 已验证 Tauri 在同类工具中的可行性。

### 1.6 市场空白结论

"安卓/iOS 原生 APP → 局域网 TCP → Linux/Win/Mac 剪贴板"这个组合在现有竞品中是空白。最接近的 VoiceBridge 用浏览器（无法实现松手即发）+ xdotool（Linux 兼容性差），InsertKit 用 Tauri 但走云同步（延迟 + 隐私）。本品占据的生态位是：

> **免费、开源、局域网、复用输入法、剪贴板同步、跨平台原生应用**

## 2. 产品概述

### 2.1 产品定义

**BeeType** 是一款跨设备语音输入工具。它让用户在手机上用自己已安装的输入法（豆包、讯飞、微信等）进行语音转文字，识别完成的文字通过局域网即时同步到 PC 的系统剪贴板，用户在 PC 上按 Ctrl+V 即可粘贴。

一句话描述：**手机说话，电脑粘贴。**

### 2.2 产品边界

**做什么：**
- 手机端 APP 接收输入法语音转文字的结果，通过局域网 TCP 发送到 PC
- PC 端后台服务接收文字，写入系统剪贴板
- QR 码配对建立设备信任关系
- 配对状态持久化，重启自动重连

**不做什么：**
- 不做语音识别引擎——复用用户手机上已有的输入法
- 不做自动粘贴——用户手动 Ctrl+V，避免键注入兼容性问题
- 不做文件传输
- 不做剪贴板历史管理
- 不做远程控制（鼠标/键盘/屏幕）
- 不做云端中继——纯局域网，文字不过云端
- 不做账号体系——无需注册登录

### 2.3 产品架构

```
┌──────────────────┐                    ┌──────────────────┐
│   手机端 (Flutter)  │                    │  PC 端 (Tauri)     │
│                    │   局域网 TCP/JSON   │                    │
│  ┌──────────────┐  │                    │  ┌──────────────┐  │
│  │  TextField   │  │   text payload     │  │  TCP Server  │  │
│  │  ↑ IME 语音   │ ──────────────────→ │  │  ↓ 写入       │  │
│  │  按住说话     │  │                    │  │  剪贴板       │  │
│  │  松手即发     │  │   ack              │  │              │  │
│  └──────────────┘  │ ←───────────────── │  └──────────────┘  │
│                    │                    │                    │
│  ┌──────────────┐  │                    │  ┌──────────────┐  │
│  │  QR 扫码配对  │  │   配对握手          │  │  系统托盘     │  │
│  │  连接状态显示  │  │                    │  │  QR 展示     │  │
│  └──────────────┘  │                    │  │  开机自启    │  │

                                        └──────────────────┘
```

### 2.4 技术选型

| 端 | 技术 | 选型理由 |
|---|---|---|
| PC 桌面端 | Tauri 2.x + Rust | 跨平台原生安装包、clipboard/autostart/tray 官方插件、Rust 性能 |
| 手机端 | Flutter 3.x + Dart | 编译型语言低延迟、TextField 正确实现 InputConnection 接收 CJK 文本、官方桌面端支持可复用 |
| 通信协议 | TCP + JSON 行协议 | 局域网直连零延迟、JSON 易调试、行协议简单可靠 |
| 配对方式 | QR 码（PC 展示，手机扫描） | 3 步内完成、无需输入 IP/端口 |

### 2.5 设计原则

1. **极简**：一个功能，一条链路，零配置。用户装完即用，扫码即连。
2. **复用**：不自建语音引擎、不自建输入法、不做云端服务。只做"文字从手机到剪贴板"这一段管道。
3. **兼容**：剪贴板是所有桌面环境都支持的最低公约数。不碰键注入，不碰 XTEST/Wayland 那一层。
4. **隐私**：文字仅在手机和 PC 两台设备间流动，不过任何第三方服务器。

### FR-1：QR 码配对

**描述**：PC 端生成包含连接信息的 QR 码，手机端扫描后建立配对关系。

**输入**：用户点击 PC 端托盘菜单"显示配对码"
**输出**：PC 端弹出窗口展示 QR 码；手机扫描后配对成功，双方存储配对凭证

**QR 码内容**：
```json
{
  "ip": "192.168.1.100",
  "port": 8765,
  "code": "482916"
}
```

**配对握手流程**：
1. 手机扫描 QR 码，解析出 `ip`、`port`、`code`
2. 手机向 `ip:port` 发送 TCP 连接
3. 连接建立后发送 `hello` 消息：`{"type":"hello","code":"482916"}`
4. PC 端校验 `code`，匹配则回复 `hello_ack`：`{"type":"hello_ack","ok":true}`
5. 双方持久化配对凭证（IP + 端口 + 配对码 + 设备名）
6. 手机端显示"已连接：陈先生的 Deepin"

**配对码规则**：
- 6 位数字，PC 端启动时自动生成，每次配对成功后重新生成
- 配对码不存明文，PC 端存 hash，校验时比对

**边界约束**：
- 配对码有效期：PC 端展示 QR 码后 5 分钟内有效，超时需重新展示
- 同一时间只允许一个手机配对（MVP 不支持多手机）
- 配对失败 5 次后冷却 60 秒（防暴力扫描）

---

### FR-2：设备连接管理

**描述**：配对完成后，手机端自动维护与 PC 的 TCP 长连接，断线后自动重连。

**输入**：配对凭证（IP + 端口 + 配对码）
**输出**：稳定的 TCP 长连接，双向心跳保活

**连接生命周期**：

| 状态 | 触发条件 | 行为 |
|---|---|---|
| 已配对未连接 | APP 启动 / 配对成功 | 尝试建立 TCP 连接 |
| 连接中 | 正在握手 | 等待 3 秒超时 |
| 已连接 | 握手成功 | 心跳保活，可发送文本 |
| 重连中 | 连接断开 | 间隔 2/4/8/16 秒指数退避重试 |
| 连接失败 | 重连 5 次仍失败 | 提示"无法连接 PC，请检查网络" |

**心跳机制**：
- 连接空闲 15 秒后发送 `ping`
- PC 端收到 `ping` 回复 `pong`
- 10 秒内未收到 `pong` 判定连接断开

**断线处理**：
- 手机端断线：自动重连，重连期间 APP 显示"连接中..."
- PC 端断线：托盘图标变灰，等待手机重连
- 重连成功后恢复到"已连接"状态，无需重新扫码

---

### FR-3：语音文字接收与发送

**描述**：手机端 APP 提供一个文本输入框，用户使用已安装的输入法语音功能，按住说话、松手后输入法提交文字，APP 检测到文字后立即通过 TCP 发送给 PC。

**输入**：用户通过输入法语音转文字，输入法通过 `InputConnection.commitText()` 提交文本
**输出**：文本通过 TCP 发送到 PC，PC 回复 ack

**交互流程**：
1. 用户打开 APP → 自动连接 PC → TextField 自动获焦 → 输入法弹出
2. 用户按住输入法麦克风说话
3. 松手 → 输入法识别完成 → `commitText()` → Flutter `onChanged` 回调触发
4. APP 将文本打包为 JSON：`{"type":"text","id":"uuid","text":"识别内容","ts":1730000000000}`
5. 通过 TCP 发送到 PC
6. 等待 PC 回复 ack：`{"type":"ack","id":"uuid","ok":true,"pasted":true}`
7. 收到 ack 后清空 TextField，等待下一次输入

**边界约束**：
- 单条文本上限：256KB（超长文本截断并提示）
- 文本编码：UTF-8，支持中文、英文、emoji、混合内容
- 发送超时：5 秒内未收到 ack 则提示"发送失败"
- TextField 在发送后自动清空，准备下一次输入
- 连接断开时 TextField 不可输入，显示"未连接"

---

### FR-4：剪贴板写入

**描述**：PC 端收到手机发来的文本后，写入系统剪贴板，覆盖剪贴板当前内容。

**输入**：TCP 收到的 JSON 消息 `{"type":"text","text":"..."}`
**输出**：系统剪贴板内容被替换为新文本

**写入逻辑**：
1. 收到 text 消息，解析出 `text` 字段
2. 调用 Tauri clipboard-manager 插件写入剪贴板
3. 回复 ack：`{"type":"ack","id":"uuid","ok":true}`
4. 发送系统通知（可选）：`BeeType: 已收到文字（N 字）`

**剪贴板保护策略**：
- 写入前不保存旧剪贴板内容（MVP 简化，不做恢复）
- 如果剪贴板当前包含非文本内容（如图片），不覆盖，回复 ack 并标注 `clipboard_non_text: true`，发送系统通知提示用户"剪贴板有图片，未覆盖，请手动 Ctrl+V 或清除图片后再发"

**边界约束**：
- 写入操作超时：2 秒
- 写入失败时回复 ack 并标注 `ok: false, error: "clipboard_write_failed"`

### FR-7：配对状态持久化

**手机端存储**：
- 使用 Flutter shared_preferences 或 secure storage

2. 手机端启动 → 读取配置 → 如果有配对记录 → 自动尝试连接记录的 IP:port


#### 7.3.3 TextField 与输入法交互

```dart
TextField(
  autofocus: true,               // 连接成功后自动获焦 → 弹出输入法
  maxLines: null,                 // 支持多行
  textInputAction: TextInputAction.newline,  // 回车插入换行而非提交
  onChanged: (text) {
    // 输入法 commitText 后触发
    // 防抖：输入法可能多次 commitText（逐字提交）
    // 策略：debounce 300ms，最后一次 commitText 后 300ms 无变化才发送
    _debounceSend(text);
  },
  controller: _controller,
)
```

**防抖策略**：
- 不同输入法的 commitText 行为不同：
  - 豆包/讯飞：松手后一次性 commitText 整句
  - 部分输入法：逐字/逐词 commitText
- debounce 300ms：最后一次 commitText 后 300ms 内无新变化才打包发送
- 收到 ack 后清空 TextField

### 7.4 通信协议设计

#### 7.4.1 消息格式

JSON 行协议：每条消息为一行 UTF-8 JSON，以 `\n` 分隔。

| 消息类型 | 方向 | 格式 |
|---|---|---|
| hello | 手机→PC | `{"type":"hello","code":"482916","device":"陈先生的手机"}` |
| hello_ack | PC→手机 | `{"type":"hello_ack","ok":true,"device":"陈先生的 Deepin"}` |
| text | 手机→PC | `{"type":"text","id":"a1b2c3","text":"内容","ts":1730000000000}` |
| ack | PC→手机 | `{"type":"ack","id":"a1b2c3","ok":true,"clipboard_non_text":false}` |
| ping | 手机→PC | `{"type":"ping"}` |
| pong | PC→手机 | `{"type":"pong"}` |

#### 7.4.2 协议约束

- 编码：UTF-8
- 行分隔符：`\n`
- 单行最大长度：256KB
- 字段说明：
  - `id`：UUID v4，用于 text/ack 配对
  - `ts`：毫秒时间戳，用于延迟统计
  - `code`：6 位数字配对码
  - `device`：设备名（用户可读，用于状态展示）

### 7.5 配对码安全设计

```
生成：
  PC 端启动时 → 生成 6 位随机数字 code
  → 存储 hash(code) 到 config.json
  → 展示在 QR 码中（明文，用于手机端提交）

校验：
  收到 hello{code}
  → hash(收到的 code) == config 中存储的 hash?
  → 匹配 → hello_ack{ok:true}
  → 不匹配 → 记录失败次数，5 次后冷却

重新生成：
  配对成功后 → 重新生成 code 和 hash
  → 下次配对需重新扫码
```
